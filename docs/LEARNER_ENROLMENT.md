# Learner enrolment and scoped rosters

Administrators register learners into a real class with a school-issued admission reference, given name and family name. Batch size is 1–50; normalized references must be unique in a request and within a school. Names are canonical PEOS identity data in identity.person_names. organisation.learner_registrations binds a school reference to a person; LEARNER organisation membership and class membership are created in the same transaction. No account, credential, external consent or learning record is created by enrolment.

POST /v1/admin/schools/[schoolId]/classes/[classId]/learners accepts {learners:[{admissionNumber,givenName,familyName}]}. Rejects extra fields such as submitted person IDs, school IDs, birth dates and authority. Repeating matching data returns ALREADY_ENROLLED. A current school registrant with matching names may be added to another class (ENROLLED); this supports class groups and does not silently transfer/remove existing enrolment. Existing names or inactive membership conflicts return CONFLICT without changing that row. Other validated rows may succeed; results remain in input order. Unexpected failures roll back the transaction. Lost HTTP results require refreshing/retrying: the school reference prevents a duplicate person in that school. No automatic retry.

School-level transaction advisory locks serialize registration and class removal. School authority and active class are locked for writes. Unknown references create new canonical people; never auto-merge across schools or match people solely on names. Cross-school transfers, identity merging, changing reference/name and school withdrawal need a separately reviewed lifecycle. No national ID, email, birth date or sensitive narrative is collected in this slice.

GET at the same endpoint lists the active roster; DELETE /learners/[personId] ends only that class membership, retaining school registration and records. Teachers have GET /v1/schools/[schoolId]/classes/[classId]/roster. Every teacher read requires current active person, school, STAFF membership, TEACHER role and exact same-school class assignment. Only active learner persons, current LEARNER memberships and active registrations appear. Removing a class assignment, role or enrolment blocks subsequent dependent access. Learner context picks an actually assigned class for the requesting teacher when a learner has multiple class memberships.

Rosters use deterministic ordering and 100-row pages with nextOffset. Reads and writes are audited; names, school references, CSVs and raw tokens are not placed in audit metadata. New tables use RLS with no browser-role grants. They are accessed only through authenticated server APIs.

Tests use isolated CI fixtures; production learners must be entered by the authorized school administrator.
