# Family billing authority v1

Prepared feature, default off: PEOS_FAMILY_BILLING_ENABLED. No grant is created by migration, school invitation acceptance or a confirmed contact relationship. A current school Principal explicitly confirms billing authority for one verified school contact, one learner, one school, a bounded action set and an expiry of at most 400 days. The Principal cannot grant access to themselves. Read access is required; plan-accept/proof-submit actions are independent permissions and do not imply those product workflows exist.

GET/POST /v1/finance/schools/:schoolId/family-billing list confirmed eligible contacts and create a grant. POST /:grantId with acknowledgement:true revokes it. Administrative inputs cannot nominate a different adult/child: canonical scope comes from the current confirmed relationship. Creation serializes on that relationship and replays only identical scope/actions/expiry by the same issuer; different settings require revocation and a new grant. No role or staff membership is added. No notification is sent.

GET /v1/family/billing lists only the session person's currently effective grants, minimal learner names/reference, school and permitted actions. POST /v1/family/billing/:grantId/authorize accepts action only and returns a strict family-billing-v1 decision bound to current person, grant, school, learner and action, with a short expiry (30 seconds). Consumers must recheck on every request; expiry is not permission to cache authority. No sibling, other family, learner narrative or banking data is returned. No grant yields an empty directory; denied decisions are audited without private payloads.

Eligibility is re-evaluated against the active confirmed relationship/invitation, active adult/learner/school, active learner registration and current membership, unexpired/unrevoked grant and the grant issuer's current school Principal role/membership. Withdrawal of the school relationship or grant invalidates future decisions. Parent can withdraw their own billing grant even if the relationship later becomes unavailable. Revocation keeps original grant records and first revoker/time; audit records each action.

Routes are private/no-store and authenticated through current PEOS session introspection. Strict bounded bodies; feature off returns before storage. The new table has RLS enabled and PUBLIC privileges revoked. Existing server database-role strategy remains unchanged. No public/client direct table access or new credentials.

Validation: unit tests for acknowledgement, action limits and default-off; PostgreSQL lifecycle tests for explicit grant, independent Principal authority, duplicate replay, wrong family, unsupported action, expired grant, ended learner membership, ended issuer role, relationship withdrawal, owner revocation and audit minimisation. Production is not activated. Coordinate SpaceCase strict adapter and parent-only invoice projection before any Preview activation; proof uploads and accepted-plan writes are separate gates.
