# School registration intake

Applicants authenticate with their own PEOS person. Request submission, private progress and withdrawal do not create an organisation, staff membership or role. The nominated principal email is unverified and is never sent an invitation by this workflow. School details are a proposal, not canonical school identity.

Current global founders may list summaries, deliberately open full details, investigate possible school-name/EMIS matches, begin review, request information or decline with an applicant-visible message. A requester cannot review their own request. No approval/provisioning action exists. Existing-school matches are hints, not ownership proof. Applicant information is not included in audit metadata.

Request retries use a per-applicant submission key and require the same normalized payload. An active same-name request for that applicant is rejected without exposing anyone else's applications. Limit five active and twenty-five newly submitted requests in twenty-four hours. Owner withdrawal and founder review serialize through revision and row locks. Wrong owner, stale revision, inactive person, withdrawn request and revoked founder roles fail closed.

Changes requested after submission currently require withdrawal and corrected resubmission or contact with the pilot coordinator. Documents, identity numbers and private learner data are not requested. Evidence collection/retention, nominee acceptance, independent verification, MFA/step-up, provisioning and principal replacement are separate unreleased gates. Retention/deletion policy must be finalized before general availability or document collection.

## Migration preparation

`prepare-migrations.yml` invokes pinned Supabase CLI for SQL proposals with safe names. It has read-only repository permissions and no database credentials. It logs checksums and preserves generated SQL as a fourteen-day workflow artifact. Review generated files before copying them into the custom PEOS `db/migrations` directory; the workflow never applies SQL and must not be used to apply a duplicate proposal.

The initial `20261028151307_school_registration.sql` was generated by workflow run 40713666250. Production rollout requires CI PostgreSQL checks, schema/privilege verification, backend deployment, then the SpaceCase UI. Do not run integration fixtures against production.
